# AI Village Resource Exchange Network

**A rural circular economy platform connecting villagers who have idle resources with those who need them — powered by AI matching, voice input in local languages, trust-based reviews, and offline-first sync.**

Built for the **Social Impact / Sustainability** track.

---

## The Problem

In villages, expensive resources sit underused every day:
- Tractors remain idle for days at a time.
- Farm equipment is borrowed informally, with no record of who has what.
- Water pumps, generators, and tools are hard to find when actually needed.
- Excess crops and leftover materials go to waste.

There is no simple way for villagers to know who has what and who needs what.

## The Solution

AI Village Resource Exchange Network lets villagers:
- **List** equipment, tools, or produce to rent, lend, sell, or exchange.
- **Speak** listings using voice commands in local languages — no literacy barrier.
- **Get matched** with nearby users through AI-powered recommendations.
- **See demand forecasts** — e.g. "Farmers nearby may need a water pump next week due to expected dry weather."
- **Use the app with poor internet**, since listing data syncs automatically once a connection is available.
- **Trust who they're trading with**, via a verification badge and review system built on trade history.
- **Report issues** through a built-in complaint flow if a trade goes wrong.
- **Use the app in their own language** — the full interface is available in English, Hindi, and Telugu.
- **Get notified** when someone requests their listing, when a request is accepted or completed, or when they receive a review.

## Core Features

| Feature | Description |
|---|---|
| Resource listings | Create, browse, and search equipment/tool/produce listings by category and distance |
| Voice input | Speak a listing instead of typing, in English, Hindi, or Telugu |
| Multi-language UI | Onboarding, navigation, forms, and My Trades are fully available in English, Hindi, and Telugu |
| AI matching | Gemini-powered explanation of why a listing fits a nearby request |

| Offline-first sync | Local cache for Browse + queued listing uploads while offline, syncing automatically on reconnect |

| Reviews | Star ratings and comments left after a completed trade |
| Complaint box | Report issues (damaged, stolen, no-show) tied to a specific trade — visible only to the two parties involved |
| Notifications | In-app alerts for new requests, accept/reject/completion updates, and new reviews — generated by database triggers, not client code |
| Impact stats | Aggregate view of listings shared, requests fulfilled, and estimated idle-hours saved |

## Tech Stack

- **Frontend:** Flutter (Web-tested, Android-capable), built with AI-assisted development (Windsurf, later Cursor)
- **Backend:** Supabase — Postgres, Auth, Storage, Row-Level Security, Edge Functions
- **Offline sync:** drift/sqflite + connectivity_plus (Browse caching and queued listing uploads)
- **AI matching, trust summaries & forecasting:** Google Gemini (`gemini-3.5-flash`), called through a Supabase Edge Function proxy — see [How the AI Layer Works](#how-the-ai-layer-works)
- **Voice input:** Flutter `speech_to_text`
- **Weather data:** OpenWeatherMap (free tier), called directly from the client
- **State management:** Riverpod
- **Navigation:** GoRouter
- **Localization:** a lightweight custom string map (`lib/l10n/app_strings.dart`) — English, Hindi, Telugu

## Getting Started

### Prerequisites
- Flutter SDK installed
- A Supabase account and project
- API keys for Gemini and OpenWeatherMap (both have free tiers)
- Supabase CLI (`npx supabase`, no global install needed)

### Setup

```bash
git clone <repo-url>
cd village_exchange
flutter pub get
```

Create a `.env` file in the project root (already git-ignored):

```
SUPABASE_URL=
SUPABASE_ANON_KEY=
OPENWEATHER_API_KEY=
```

> Note: `GEMINI_API_KEY` is **not** in `.env` — it lives only as a Supabase Edge Function secret (see below), never bundled into the client. See [How the AI Layer Works](#how-the-ai-layer-works) for why.

### Supabase configuration

1. **Run the schema migrations**, in this order, in the Supabase SQL editor:
   - `01_schema.sql` — users, listings, requests tables + RLS
   - `02_seed.sql` — demo villagers and listings
   - `03_storage_and_constraints.sql` — listing-photo storage bucket + category constraint
   - `04_notifications.sql` — notifications table + triggers
2. **Enable the Email auth provider**: Authentication → Providers → Email. (The app does not use Supabase's Phone provider — see [Authentication](#authentication) below for why.)
3. **Deploy the two Edge Functions**:
   ```bash
   npx supabase login
   npx supabase link --project-ref <your-project-ref>
   npx supabase functions deploy ensure-demo-user
   npx supabase functions deploy gemini-generate
   npx supabase secrets set GEMINI_API_KEY=your_real_gemini_key
   ```
   `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are auto-injected into every Edge Function — no need to set those.
4. In the dashboard, open each function and confirm **Verify JWT** shows **OFF**. (Supabase's CLI has a known intermittent issue where this doesn't always take effect from the deploy command alone — worth a visual check.)

### Authentication

This build uses a **demo-mode login**: phone number + a fixed OTP (`123456`), not real SMS. Real SMS OTP requires a paid provider, and Indian numbers additionally require TRAI DLT registration — neither is feasible in a hackathon build window.

Behind the scenes, the app derives a deterministic email/password from the phone number and signs in through real Supabase Auth via the `ensure-demo-user` Edge Function, so Row-Level Security and every other Postgres policy behave exactly as they would with real phone auth — only the delivery mechanism for the OTP is simulated. This is a deliberate, documented trade-off, not an oversight.

### Run the app

```bash
flutter run -d chrome --web-port=8080
```

Using a fixed port keeps Supabase's browser-stored session consistent across restarts during testing.

## How the AI Layer Works

- **Matching:** listing text, category, and location are sent to Gemini via the `gemini-generate` Edge Function, which returns a short explanation of why a listing fits a nearby request.
- **Trust summary:** a trader's rating history and complaint count are summarized by Gemini into a one-line description shown next to their verification badge.
- **Demand forecasting:** OpenWeatherMap data plus simple rule-based logic (no rain forecast + nearby active produce listings) is passed to Gemini to generate a natural-language alert banner on Home.
- **Language-aware output:** all three prompts include an explicit instruction ("Please respond in Hindi" / "...in Telugu") when the app's selected language isn't English, so AI-generated text matches the rest of the interface.
- **Why an Edge Function, not a direct client call:** Google's Generative Language API does not return CORS headers for direct browser requests, so calling it straight from Flutter Web is blocked regardless of API key validity. Routing through a Supabase Edge Function — which does set CORS headers — fixes this and, as a bonus, keeps the Gemini key server-side only.
- **Voice:** treated purely as an alternate input method — transcribed text flows through the same listing pipeline as typed input, no separate voice backend needed.

---

## Trust & Safety

- Every new user starts at `trust_score = 5.0`, badge `New trader`.
- After each review or complaint, a Postgres trigger — not client code — recalculates `trust_score` (weighted average of ratings, penalized by unresolved complaints) and `badge_level` (Verified / Member / New trader / Flagged). This can't be bypassed by a client-side bug.
- Complaints are visible only to the two parties involved in that trade, never published publicly.

## Known Limitations (Demo Scope)

- **Auth is demo-grade** — see [Authentication](#authentication) above. Not suitable for production as-is.
- **Notification message text is English-only.** The rest of the interface is fully localized; the sentences generated by the notification database triggers are not yet templated per language.
- **Offline sync covers Browse caching and queued listing uploads only** — requests, reviews, and complaints still require connectivity.
- **Voice recognition script quality depends on the browser/device.** Desktop Chrome's Web Speech API can be less reliable for native Devanagari/Telugu script output than Android's on-device recognizer — testing on an Android device is recommended before a live demo.
